How Hound works.

A behavioral execution monitor for developers. Hound classifies every command by source — Claude Code, Cursor, npm install, terminal, script — and flags when behavior falls outside expected scope.

The problem Hound solves

You run a lot of code you didn't write.

AI coding tools like Claude Code and Cursor generate hundreds of commands per session. Package managers execute postinstall scripts. Setup scripts from README files do whatever they want. Most of the time, everything is fine. But you have no way to know that — until now.

Traditional security tools ask "is this known malware?" That's the wrong question for developers. The question is: "is this consistent with what this workflow should be doing?" An npm install that reads ~/.ssh/id_rsa isn't necessarily known malware — but it's absolutely outside expected scope.

Hound answers the right question. It knows what each execution source is supposed to do, and it tells you when something steps outside that. Clean installs and builds produce zero output. Scope violations produce a plain-English trace explaining exactly what happened and why it matters.

The approach

Watch what programs do, not what they look like.

Hound observes four independent sensor streams: file system events, process spawning, network connections, and persistence mechanism changes. Each sensor generates atomic signals. The detection engine evaluates those signals against 165 tests. The correlation engine aggregates signals that fire together into incidents with a confidence score.

An incident requires a minimum of 35 points to generate an alert. Most atomic signals score between 6 and 24 points individually. The correlation engine adds bonuses for tight time windows (all signals within 30 seconds: +8 points) and repeat offenders (single PID driving 3+ signals: +8–12 points).

File system events ──┬ Process spawning ──┤ Detection engine ──→ Incident correlator ──→ Response engine Network connections ──┤ (165 tests) (scoring + MITRE) (kill / quarantine) Persistence changes ──┘

Sensor layer

Four independent sensor subsystems.

Each sensor runs independently and generates atomic signals. Sensors never call subprocesses or shell out to system utilities except where noted. All sensor work happens within a 50ms per-tick CPU budget.

File Monitor

Uses macOS FSEvents API (push-based, not polling). Watches 11 directories: Downloads, Desktop, Documents, LaunchAgents, LaunchDaemons, SSH keys, AWS credentials, BTM database, and periodic script directories. Detects file creation, modification, permission changes, quarantine attribute changes, and magic bytes mismatches — executables disguised as PDFs or images.

~18 microseconds mean per tick

Process Monitor

Uses sysinfo kernel API — no subprocess spawning. Records PID, parent PID, command, arguments, executable path, process kind, parent kind. Classifies processes as system, browser, interpreter, user app, or unknown. Classifies paths as downloads, user space, system space, persistence locations, or unknown.

~35 milliseconds mean per tick

Network Monitor

Polls lsof for active connections. Tracks per-PID connection history across ticks. Detects C2 beaconing patterns: repeated connections to the same external IP at regular intervals. Apple (17.0.0.0/8) and Google IP ranges suppressed from beaconing alerts.

~17 milliseconds mean per tick

Persistence Monitor

Watches LaunchAgents and LaunchDaemons directories via FSEvents. Polls crontab for modifications. Monitors BTM (Background Task Management) database file changes. Detects login hook installation via com.apple.loginwindow defaults domain.

~8 milliseconds mean per tick

Detection engine

165 detection tests. All passing.

Each detection function is independently testable with both positive cases (should detect) and negative cases (should not false-positive on normal Mac activity). Detections fire atomic signals, not incidents — a single signal is rarely actionable on its own.

The correlation engine aggregates signals across a 60-second window. Signals on the same file path or from the same PID are grouped. The resulting incident score determines whether to alert and what response action to take. A persistent SQLite baseline at runtime/baseline.db reduces scores for processes and connections seen repeatedly over time.

Response engine

When to act, and when to hold back.

Hound defaults to Simulation Mode — it detects, correlates, and alerts, but never takes action. Real response requires explicit user opt-in in Settings.

When response is enabled, the engine follows strict guardrails. It will never kill a system process, a browser, or anything in /System or /Applications. It will never quarantine a file with a safe extension (jpg, png, pdf, docx, mp4, txt). Whitelist entries are hot-reloadable from agent-config.toml — no restart required.

Process kill threshold85 points
File quarantine threshold75 points
Alert-only (no action)Below 75 points

Every response action is logged to response-audit.jsonl in plain JSON with timestamp, action type, process name, path, score, and whether the action was simulated or real. Quarantined files are recoverable by hash from runtime/quarantine/ with SHA-256 manifest verification.

The response engine evaluates guards in order: (1) system/browser guardrails — hard block, (2) whitelist check — hard block with event logged, (3) simulation mode check, (4) act. A process that passes all guards in simulation mode is logged as a simulated action only.

Performance

16 MB of memory. Invisible on your Mac.

Every subsystem has a 50ms per-tick CPU budget. The throttle system adds 50ms to the next sleep if a subsystem exceeds budget. In practice, all subsystems are well within budget on both Apple Silicon and Intel hardware.
